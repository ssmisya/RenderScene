## 2. assets/textures：渲染素材

这些是平面图片，不是模型。主工程已把它们内嵌，因此单独打开主工程不依赖外部下载；但重新运行生成器或更换材质仍要保留外部素材。

| 文件 | 表达什么 | Blender 中的用途 |
|---|---|---|
| `brick_diff.jpg` | 砖墙的颜色和表面色差 | Base Color 输入，颜色贴图 |
| `brick_nor_gl.jpg` | 砖墙微小凹凸方向，OpenGL 法线格式 | Non-Color → Normal Map 节点 → Normal 输入；不是位移几何 |
| `brick_rough.jpg` | 砖墙表面的粗糙程度 | Non-Color → Roughness 输入 |
| `paving_diff.jpg` | 小块铺石的颜色 | 铺石 Base Color 输入 |
| `paving_nor_gl.jpg` | 小铺石与砖缝的微凹凸 | 法线输入，处理方式同砖墙 |
| `paving_rough.jpg` | 小铺石的粗糙程度 | Roughness 输入 |
| `sky.hdr` | 高动态范围天空环境 | World 的 Environment Texture，提供背景及环境光 |

`brick_*`、`paving_*` 为 1K 图像，天空为 2K HDRI。大块广场花岗岩、部分金属和其他材质还使用主工程中的程序化节点，因此不是每种可见材质都对应一张外部图片。

**更换外部同名图片不保证主工程立即变化**：主工程已有内嵌版本，需要在 Blender 中明确替换/重新加载图像，或重新生成工程。

## 5. game：给游戏引擎的资产和辅助数据

| 文件 | 作用 | 怎样使用 |
|---|---|---|
| `Sophia_Square.glb` | 当前版可见场景网格与便携 PBR 材质 | 导入支持 glTF 的引擎或 Blender。当前导出不包含相机、灯光，需在引擎里设置光照和观察相机 |
| `Sophia_Collision.glb` | 当前版 125 个简化碰撞代理的网格 | 导入后用作静态碰撞形状，关闭可见渲染；单纯导入文件不会自动完成所有引擎碰撞设置 |
| `colliders.json` | box、cylinder、polygon 的尺寸、坐标、旋转和名称 | 写引擎加载器时从数据生成碰撞体，或核对代理参数；非凸 polygon 不能直接当单个凸碰撞体 |
| `map_metadata.json` | 出生参考点、眼高、胶囊半径、环绕路线、地理原点和轴向 | 配置自己的玩家控制器与导航。出生参考位置包含眼高，不能未经适配就当作任何引擎角色根节点的位置 |
| `export_validation.json` | 两个 GLB 文件头、网格、内嵌图像、回导结果 | 排查导出完整性；不是目标引擎性能测试 |
| `route_validation.json` | 外部环绕路线的 408 次二维位置采样结果 | 参考路线是否穿入已有障碍；没有模拟实际角色动力学，也不是 NavMesh |

Blender 坐标以 Z 向上，单位为米；GLB 导出为 Y 向上。当前 JSON 保留 Blender 坐标，若手写加载器，转换关系是 `(x, y, z) → (x, z, -y)`。许多引擎的导入器已经转换 GLB，不要对已转换的模型再重复旋转。

GLB 简化了 Cycles 专用程序化材质，不能期待与主工程像素级一致。这里没有玩家控制器、室内、武器、敌人、自动 LOD、烘焙 NavMesh 或帧率验收结果。

## 6. scripts：七个脚本逐一说明

这些脚本依赖 Blender 的 `bpy`，应由 Blender 运行，而不是直接执行 `python3 脚本.py`。下面推荐使用单独的后台 Blender 进程，避免改变你正在界面里编辑的未保存场景。

| 脚本 | 实际行为 | 什么时候用 / 影响 |
|---|---|---|
| `build_scene.py` | 清空运行中的场景，按代码生成几何、材质、周边、相机和代理，保存主工程、碰撞 JSON、地图元数据、统计 | 改了生成代码或地图输入、想从头生成时用。**会覆盖主工程，手工编辑不会被自动合并回来** |
| `render_scene.py` | 加载指定主工程后，选择机位、设分辨率与采样，渲染 PNG | 日常最常用；保存图片，不保存对主工程的参数变化。会覆盖同名图片 |
| `export_game.py` | 在运行中的临时场景中简化材质、移除可见网格修改器、调整 UV、文字转网格，再输出两个 GLB | 把已保存的修改同步给游戏资产时用。不会把临时简化结果保存回主工程；如果在 GUI 中直接运行，当前内存中的场景会被改变 |
| `verify_game.py` | 重置运行中的 Blender 场景，分别导入两个 GLB 并检查文件和图像，写检查 JSON | 检查导出是否可读取；**会清空运行中的场景**，用后台进程执行 |
| `finalize_render.py` | 重设固定主视角、1920 × 1280 与 96 samples，保存主工程，检查后渲染五张图 | 恢复本交付的固定展示设置时用；**会覆盖已修改的主视角和部分工程设置**。一般渲染用 `render_scene.py` 即可 |
| `deliver_pipeline.py` | 顺序运行 `finalize_render.py` → `export_game.py` → `verify_game.py`，最后检查五张 PNG | 重新生成整套渲染和游戏导出；**会保存工程并重设主视角**。它不调用建模生成器，也不更新 ZIP、MANIFEST、路线检查或场景统计 |
| `relocate_project.py` | 把素材路径及输出路径改成当前工程旁的相对路径，然后保存主工程 | 项目搬家后修复路径时用；本次迁移已执行，日常不需要重复运行 |

`build_scene.py` 直接使用 `assets/textures/`、`references/map_aligned.json`；其他脚本大多依据打开的 `.blend` 所在目录找输出位置。因此打开旧工程再运行脚本，会对旧工程目录写文件，要先确认打开的是当前主工程。

### 本机命令用法

在终端先设置当前目录和 Blender 路径：

```sh
cd '/Users/songmingyang/Library/Mobile Documents/com~apple~CloudDocs/Desktop/projects/Local tasks/blender'
BLENDER_BIN='/Applications/Blender.app/Contents/MacOS/Blender'
```

日常渲染一张人眼视角：

```sh
"$BLENDER_BIN" -b Harbin_Sophia_Square.blend --python scripts/render_scene.py -- --view eye --width 1920 --samples 128
```

`--view` 可选：`hero`、`eye`、`east`、`overview`、`detail`、`all`。`--width` 是像素宽度，高度固定为宽度的 2/3；`--samples` 是采样数，数值更高一般耗时更长；加 `--cpu` 可使用 CPU。脚本默认尝试这台 Mac 的 Metal GPU。

渲染全部五个机位：

```sh
"$BLENDER_BIN" -b Harbin_Sophia_Square.blend --python scripts/render_scene.py -- --view all --width 1920 --samples 128
```

导出修改后的游戏资产，再检查：

```sh
"$BLENDER_BIN" -b Harbin_Sophia_Square.blend --python scripts/export_game.py
"$BLENDER_BIN" -b --python scripts/verify_game.py
```

只有需要按代码重建时，才执行：

```sh
"$BLENDER_BIN" -b --python scripts/build_scene.py
```

重建并输出一张低分辨率过程预览：

```sh
"$BLENDER_BIN" -b --python scripts/build_scene.py -- --render-preview
```

其他维护脚本按需使用：

```sh
# 重设展示相机，保存工程并渲染五张图
"$BLENDER_BIN" -b Harbin_Sophia_Square.blend --python scripts/finalize_render.py

# 重设展示设置、保存、渲染、导出、回导检查
"$BLENDER_BIN" -b Harbin_Sophia_Square.blend --python scripts/deliver_pipeline.py

# 修复搬家后的相对路径并保存
"$BLENDER_BIN" -b Harbin_Sophia_Square.blend --python scripts/relocate_project.py
```

## 7. 六个日志文件

日志用文本编辑器打开，查执行步骤、报错或是否出现完成标记。它们不会驱动工程，旧日志也不会自动跟随每次脚本运行刷新；只有把新命令输出重定向到同一个日志文件才会更新。

| 文件 | 对应记录 |
|---|---|
| `build.log` | 建模生成过程，包含保存和统计信息 |
| `render.log` | 某轮五机位渲染过程 |
| `export.log` | 某轮 GLB 导出过程 |
| `game_validation.log` | 某轮 GLB 回导检查 |
| `delivery.log` | 最后一轮完整交付流程，包含渲染、导出、回导与完成标记 |
| `relocation.log` | 把主工程迁移到当前目录后的路径修复记录 |

完整流程里的 `export_validation.json` 可能比单独的 `game_validation.log` 新，因为完整流程把输出写在 `delivery.log`。判断结果时看对应流程和时间。

| `09_GAME_MARKERS` | 出生参考点与路线空物体 | 导航和角色放置参考；空物体不是可见角色或自动运行的脚本 |

## 9. 最常用的四种工作方式

### 看场景和出图

打开主工程 → 选相机 → F12。若 F12 被系统功能键占用，可用 Render → Render Image。**在 Blender 界面按 F12 只生成 Render Result，通常还需在渲染结果窗口选择 Image → Save As 才写出图片。** 上面的后台渲染脚本会自动保存 PNG。

只想快速看现成效果，用浏览器打开 `preview.html` 或直接看 `renders/`。

### 手工精修模型

在 Blender 中编辑主工程，保存后用 `render_scene.py` 渲染，用 `export_game.py` 导出。手工精修后不要为了“刷新”去运行 `build_scene.py`，它会重新按代码生成并覆盖精修。

如果希望这些修改以后可以重复生成，还需要把对应变化反映到生成器代码中；当前没有从手工工程自动反写生成器的功能。

### 调整程序化生成逻辑

修改 `scripts/build_scene.py` 或对应地图/素材输入 → 备份当前手工成果 → 运行重建 → 查看生成结果 → 渲染/导出。**手动修改 `colliders.json` 不会自动修改 `.blend` 内的碰撞体**，手动改 GLB 也不会自动同步回主工程。

### 做游戏地图

导入 `game/Sophia_Square.glb` → 配置引擎光照和材质 → 从 `Sophia_Collision.glb` 或 `colliders.json` 创建静态碰撞 → 根据 `map_metadata.json` 设置自己的玩家控制器 → 在引擎中检查行走、烘焙导航与优化性能。

只有模型与代理存在，不代表已经有可运行的 FPS 游戏。当前版是外景地图资产，实景精度边界请看 `REFERENCES.md`。

ZIP、JSON 统计/检查报告和图片都是某次输出的快照，不会与主工程实时双向同步。当前项目没有一个命令自动刷新所有这些文件。
